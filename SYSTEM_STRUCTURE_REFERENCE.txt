1. SYSTEM PURPOSE

DepotManager simulates customers collecting parcels from a depot. Customers wait in a first-in-first-out
queue. A depot worker processes one customer at a time, finds the requested parcel, calculates its fee,
releases it when successful, records significant events and produces an end-of-day report.

The system must remain consistent across:
- the Part 1 use-case model;
- the Part 1 class diagram;
- the Part 1 three-tier architecture model;
- the Part 2 fixed Java implementation;
- the Part 2 reflective comparison.


2. SYSTEM BOUNDARY AND ACTORS

System subject: DepotManager

Mandatory external actors:

Customer
- Joins the collection queue.
- States the parcel ID they wish to collect.
- Part 1 explicitly requires Customer as an actor.
- Part 2 does not provide a customer-facing GUI. It loads customers from a file and exposes controller
  and queue operations. This is an allowed Part 1 to Part 2 difference to discuss in the reflection.

Depot Worker
- Processes the next customer.
- Looks up parcels.
- calculates collection fees.
- Releases parcels.
- Adds new parcels.
- Views outstanding parcels and processing details.
- Generates the end-of-day report.

Record Event to Log is an internal system responsibility. No actor initiates it directly.


3. MANDATORY PART 1 USE CASES

UC-01 Join Collection Queue
Actor: Customer
Outcome: Customer is added to the back of the FIFO queue with their requested parcel ID.
Part 2 mapping: DepotController.addCustomerToQueue(Customer), CustomerQueue.enqueue(Customer).
Logging: Includes Record Event to Log.

UC-02 Process Next Customer
Actor: Depot Worker
Outcome: The customer at the front of the queue is processed.
Part 2 mapping: DepotController.processNextCustomer(), Worker.processNextCustomer(...).
Logging: Includes Record Event to Log.
Workflow note: Look Up Parcel and Calculate Collection Fee occur in the normal processing flow but are
not shown as <<include>> relationships because exception paths can finish before fee calculation.

UC-03 Look Up Parcel
Actor: Depot Worker
Outcome: The requested parcel is found by its unique ID.
Part 2 mapping: ParcelMap.getParcel(String).
Exception: Handle Parcel Not Found extends this use case.

UC-04 Calculate Collection Fee
Actor: Depot Worker
Outcome: The collection fee is calculated for the located parcel.
Part 2 mapping: Worker.calculateFee(Parcel).

UC-05 Release Parcel
Actor: Depot Worker
Outcome: The successful parcel is marked collected and no longer appears as outstanding.
Part 2 mapping: Parcel.setCollected(true), coordinated by Worker.processNextCustomer(...).
Logging: Includes Record Event to Log.

UC-06 Add New Parcel
Actor: Depot Worker
Outcome: A newly arrived parcel is added to depot records.
Part 2 mapping: DepotController.addParcel(Parcel), ParcelMap.addParcel(Parcel).
Logging: Includes Record Event to Log.
Part 2 difference: The fixed minimum GUI has no required Add Parcel button, but the controller operation exists.

UC-07 View Parcels Awaiting Collection
Actor: Depot Worker
Outcome: The uncollected parcels are displayed, oldest waiting first in Part 2.
Part 2 mapping: ParcelListPanel.refresh(ParcelMap),
ParcelMap.getUncollectedSortedByDaysInDepot().

UC-08 View Current Processing Details
Actor: Depot Worker
Outcome: Customer, parcel and fee or an error result are displayed.
Part 2 mapping: ProcessingPanel.showResult(ProcessingResult).
Part 2 difference: The fixed GUI displays the most recent processing result.

UC-09 Generate End-of-Day Report
Actor: Depot Worker
Outcome: A written report contains collected parcels and fees, uncollected parcels, summary counts
and totals.
Part 2 mapping: DepotController.endDay(...), ReportWriter.writeReport(...).
Logging/output: Includes Record Event to Log and writes the shared log file.

UC-10 Record Event to Log
Actor: None; internal included responsibility.
Outcome: Significant events and errors are recorded in one shared event log.
Part 2 mapping: Log.getInstance(), Log.logEvent(String), Log.writeToFile(String).


4. APPROVED OPTIONAL OR EXCEPTIONAL USE CASE

UC-11 Handle Parcel Not Found
Type: Approved additional exceptional use case.
Condition: Requested parcel ID cannot be found.
Relationship: Handle Parcel Not Found --<<extend>>--> Look Up Parcel.
Arrow direction: From Handle Parcel Not Found to Look Up Parcel.
Outcome: Collection is not completed, parcel state is unchanged, a failure result is displayed and the
error is logged.
Part 2 mapping: Worker.processNextCustomer(...) returns ProcessingResult.failure(...); Log records it.
Logging: Includes Record Event to Log.

Only this additional use case is currently approved for the submitted design.

6. BUSINESS RULES CONFIRMED BY PART 2

Parcel identity
- Parcel IDs match C or X followed by two or three digits.
- Parcel IDs are unique in ParcelMap.

Parcel data
- Parcel stores ID, weight, length, width, height, days in depot and collected status.
- Parcel validates constructor data.
- Invalid parcel data produces InvalidParcelDataException.
- Volume = length x width x height.

Customer data
- Customer stores queue sequence number, name and requested parcel ID.
- Customer validates its constructor arguments.

Queue processing
- Customers are processed in strict first-in-first-out order.
- An empty queue returns a graceful failure result; it must not crash the GUI.

Fee formula
- fee = (weight x 0.5) + (volume x 0.1) + (daysInDepot x 0.2)
- If the parcel ID starts with X, apply a 10 percent discount.
- Round the result to two decimal places.

Collection success
- The requested parcel exists.
- The parcel has not already been collected.
- The fee is calculated.
- The parcel is marked collected.
- The event is logged.
- A successful ProcessingResult is returned.

Collection failure
- Queue is empty; or
- requested parcel is not found; or
- parcel has already been collected.
- Failure must be displayed gracefully, with no visible exception to the user.
- Failure is represented by ProcessingResult.failure(...).

- Customer 13 requests missing parcel C999.
- Customer 15 requests C101 after it has already been collected.
- C307 and C99 remain uncollected.
- Final expected result: 13 collected, 2 uncollected and total fees of £128.80.


7. AUTHORITATIVE CLASS STRUCTURE

DATA AND DOMAIN RESPONSIBILITIES

Parcel
- Fields: id, weight, length, width, height, daysInDepot, collected.
- Validates parcel data, calculates volume and tracks collected status.

Customer
- Fields: sequenceNumber, name, parcelId.
- Represents one customer and their requested parcel.

ParcelMap
- Container for all Parcel objects.
- Structure: LinkedHashMap<String, Parcel>.
- Reason: efficient lookup by unique parcel ID while retaining insertion order.

CustomerQueue
- Container for waiting Customer objects.
- Structure: Queue<Customer> backed by LinkedList.
- Reason: naturally enforces first-in-first-out processing.

Log
- Singleton shared event log.
- Exactly one lazily created instance.
- Private constructor.
- Synchronized getInstance().
- Stores events in a shared StringBuffer and writes them using UTF-8.

ProcessingResult
- Immutable value object describing success or failure.
- Contains message, optional customer, optional parcel and fee.
- Part 2 places this in the Data and Domain tier.

InvalidParcelDataException
- Checked exception for invalid Parcel construction.
- Exception is a Java library superclass, not a DepotManager application class.

BUSINESS LOGIC RESPONSIBILITIES

Worker
- Calculates fees.
- Processes the next queued customer against ParcelMap.
- Coordinates lookup, validation, parcel release, logging and ProcessingResult creation.

DepotController
- MVC Controller.
- Mediates between Views and the model.
- Owns references to ParcelMap, CustomerQueue and Worker.
- Adds parcels and customers, processes customers, loads files and ends the day.
- Notifies registered listeners after model changes.
- Must never import or reference a class from the view package.

DepotController.DepotListener
- Nested Observer callback interface.
- Declares onDepotUpdated().
- Implemented by DepotManagerFrame.
- Allows the controller to notify Views without depending on concrete GUI classes.

PRESENTATION RESPONSIBILITIES

DepotManagerFrame
- Main Swing window.
- Implements DepotController.DepotListener.
- Registers with the controller and refreshes child panels in onDepotUpdated().

ParcelListPanel
- Displays parcels awaiting collection.

CustomerQueuePanel
- Displays customers in queue order.

ProcessingPanel
- Displays the most recent ProcessingResult.

ControlPanel
- Contains at minimum Process Next Customer and End Day controls.
- Sends actions to DepotController; it does not change model objects directly.

DepotManagerApp
- Application entry point.
- Creates and connects the model, controller and view.
- Loads the initial parcel and customer files.

DATA ACCESS AND OUTPUT RESPONSIBILITIES

DataLoader
- Utility responsible for reading parcel and customer comma-separated text files.

ReportWriter
- Utility responsible for writing the complete end-of-day report.


8. REQUIRED CLASS RELATIONSHIPS

Container relationships
- ParcelMap 1 *-- 0..* Parcel (composition; role: parcels).
- CustomerQueue 1 o-- 0..* Customer (aggregation; role: waitingCustomers).

Controller relationships
- DepotController 1 -- 1 ParcelMap.
- DepotController 1 -- 1 CustomerQueue.
- DepotController 1 -- 1 Worker.
- DepotController 1 -- 0..* DepotController.DepotListener.

Result relationships
- One ProcessingResult refers to 0..1 Customer.
- One ProcessingResult refers to 0..1 Parcel.
- Worker creates ProcessingResult objects.

View relationships
- DepotManagerFrame implements DepotController.DepotListener.
- DepotManagerFrame owns ParcelListPanel, CustomerQueuePanel, ProcessingPanel and ControlPanel.
- DepotManagerFrame and ControlPanel use DepotController.
- ControlPanel uses ProcessingPanel to show the result of processing.

Utility dependencies
- DepotController uses DataLoader, ReportWriter and Log.
- Worker uses CustomerQueue, ParcelMap, ProcessingResult and Log.


9. AUTHORITATIVE THREE-TIER ALLOCATION

PRESENTATION TIER
- DepotManagerApp
- DepotManagerFrame
- ControlPanel
- ProcessingPanel
- ParcelListPanel
- CustomerQueuePanel

BUSINESS LOGIC TIER
- Worker
- DepotController
- DepotController.DepotListener

DATA TIER
- Parcel
- Customer
- ParcelMap
- CustomerQueue
- Log
- ProcessingResult
- InvalidParcelDataException
- DataLoader
- ReportWriter

External Java library class
- Exception is outside the application tiers. Prefer removing it from the submitted application class
  diagram, or label it explicitly as an external Java library class.

Required dependency direction
- Presentation Tier -> Business Logic Tier -> Data Tier.
- Presentation initiates actions through DepotController.
- Business Logic applies rules and uses domain/data services.
- Data never depends on Presentation.
- DepotController never depends on concrete View classes.
- Observer callbacks depend on the business-owned DepotListener interface, not a View type.

MVC mapping
- View: DepotManagerFrame and its Swing panels.
- Controller: DepotController.
- Model: Parcel, Customer, ParcelMap, CustomerQueue, Worker, ProcessingResult and Log, supported by
  DataLoader and ReportWriter.
- Observer: DepotController.DepotListener connects Controller notifications to View refreshes without an
  upward concrete dependency.
